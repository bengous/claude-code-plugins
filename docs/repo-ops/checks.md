# Local checks and CI

[Repo operations index](../repo-ops.md). Read when a gate fails or when the validation machinery changes.

## Local enforcement

The checks run as a ladder, from each edit to CI: the Claude Code post-edit fixer and formatter, the Stop gates, `pre-commit`, `pre-push`, then CI.

- lefthook `pre-commit`, 27 jobs in order: `block-commit-to-main`, `block-settings-json`, `sync-settings`, `sync-versions` (auto-fix), `validate-marketplace`, `validate-frontmatter`, then the nine repo-wide gates `lint-config`, `typecheck`, `typecheck-coverage` (every tracked `.ts` is in the typecheck, dot directories included, `scripts/gates/check-typecheck-coverage.ts`), `lint-ts`, `fmt`, `lint-sh`, `check-lint-disables`, `rule-registry` (on every commit, no glob: a control renamed anywhere breaks the registry entry that names it), `platform-copies` (`scripts/gates/sync-platform.ts`: every copy of `tools/platform/` holding the modules its plugin imports, each equal to its source, and no import leaving a plugin's directory, on every commit, no glob: such an import can land in any file), then `validate-vellum` and `test-vellum` on the module's paths (`vellum/hooks/*`, `vellum/src/runtime/hooks/**`, `vellum/src/platform/*`, the manifest), `validate-todos` and `test-todos` on `todos/`'s (`todos/hooks/*`, `todos/lib/platform/*`, the manifest, `todos/types/*`), `validate-secret-pane` and `test-secret-pane` on `secret-pane/`'s (`secret-pane/hooks/*`, `secret-pane/lib/platform/*`, the manifest), and the same two for `pinpoint/`, `atlas/` and `griller/` on theirs, the copy of `tools/platform/` a module can import among them (`pinpoint/lib/platform/*`, `atlas/src/platform/*`). Only the mutating jobs are order-bound: they run before the jobs that validate what they wrote. `commit-msg`: 1 job, `block-ai-signatures`, which refuses an AI co-author or a generated-with line in a commit made with `git commit` where lefthook is installed, on the owner's machine; it never runs on a commit GitHub writes, so a squash commit's `Co-authored-by: Claude` trailer on `dev` passes ([Git procedures](git.md#how-a-change-reaches-dev)). Escape hatch for recovery only: `MAIN_BYPASS=1`.
- lefthook `pre-push`, 1 script job, `gates-and-tests` (`.lefthook/pre-push/gates-and-tests.sh`): the release guard below, then `scripts/gates/run-gates.ts --committed`, every gate as CI runs it with the kits of the hooks modules the change reaches, then `scripts/gates/affected.ts test --committed`, the suites it reaches. The change is what HEAD's commits differ from the merge-base with `origin/dev`: an untracked or uncommitted file is not pushed, so it widens nothing, where the Stop's `run-gates.ts` counts both; `scripts/` always runs, and a path no unit owns runs everything (`classify` in `affected.ts` holds the map). It first unsets the variables `git rev-parse --local-env-vars` lists: a push from a linked worktree exports `GIT_DIR`, which would send the suites' temp-repo commits to the pushing repo. A script, not a `run` job, because lefthook skips or fails a pre-push `run` job on its pushed-files lookup (reason in `lefthook.yml`). The gates and tests check the working tree, not the pushed commits. A push that only deletes refs skips it: `use_stdin` passes git's ref lines to the script, and a null local oid on every line exits before any gate.
- The release guard, `scripts/releasing/check-plugin-bumps.ts --pre-push`, gets the same ref lines and reads only a line whose remote ref is `refs/heads/main`. From that line's remote oid to its local oid, with no fetch, it refuses the push and names each marketplace plugin whose directory changed while its `plugin.json` `version` did not, a change to paths the installed plugin never reads aside (`README.md`, `CHANGELOG.md`, `AGENTS.md`, `CLAUDE.md`, `docs/`, `.claude/`, and Claude Code's API types `types/claude-code.d.ts` and `types/claude-code-tools.d.ts`, listed in `isUnreadWhenInstalled`), the file its manifest names under `types` excepted, since Claude Code reads it: a plugin is matched across both catalogs by its entry's `name` and read at each side's `source`, so a moved directory is compared with where it was; a plugin the remote's `main` does not list, or one retired from the catalog, passes. It also refuses a push to `main` when the remote has none (null remote oid) or holds a commit the pushing repo lacks. A push to any other ref passes untouched, so `dev` is never blocked between a plugin change and its release-time bump. It is no `EXPECTED_COMMANDS` entry: `run-gates.ts` would run it on every push and at every Stop, red for that whole window. No CI step either: on a push to `main`, CI's `origin/main` is already the pushed commit. By hand: `bun ./scripts/releasing/check-plugin-bumps.ts <base-ref> <head-ref>`.
- The rule registry, `.claude/rule-registry.ts`, read by `rule-registry` (`scripts/gates/check-rule-registry.ts`). A rule is every text block of `AGENTS.md` and `.claude/rules/*.md` except headings and code: a paragraph, a top-level list item (CommonMark: indented 0 to 3 spaces), a table row other than the delimiter row. Each has an entry keyed by a fingerprint of its text, the first 8 hex digits of the SHA-256 of the text with its whitespace collapsed, so a rewrap keeps the key and an edit changes it. An entry holds a `quote`, the opening words of the rule, and either `held`, the controls that enforce what the rule says is checked, or `prose`, why no tool can. A lead-in covers the list that follows it only when its entry says `covers: "list"`; otherwise each item of the list has its own entry. A `held` control counts only when it runs: `gate <name>`, an entry of `expectedCommands`; `hook <path>`, a file that a command of `.claude/__settings.jsonc`'s `hooks`, a lane's `run` or a fixer's `file` or `stdin` in `.claude/agent-hooks.jsonc`, a command of a catalog plugin's `hooks/hooks.json` (`${CLAUDE_PLUGIN_ROOT}` read as the plugin's directory), or lefthook runs (`jobs`, `group: { jobs }`, `commands:`, `scripts:`, and what a script it names runs), comments left out and `$CLAUDE_PROJECT_DIR/` or `./` dropped on both sides; `lint <rule>`, a rule `oxlint --print-config` sets to error at top level, a category included, that no override turns off; `test <path>`, a file a plain `bun test` run, an extra root of `testRuns` in `scripts/gates/affected.ts`, or a hooks module's kit (`claude plugin test <plugin>`) runs. The gate fails on a rule with no entry and names the key and quote to add, on an entry that matches no rule and names the edited rule's key, and on a control that no longer runs.
- CI parity: the nine repo-wide gates and `validate-marketplace.ts` run again in CI with the same arguments. `validate-frontmatter.ts` runs on staged files in `pre-commit`, with `--all` in `pre-push` and CI. Neither `bun test` command runs in `pre-commit`; the hooks modules' kits (`test-vellum` and `test-todos`, `claude plugin test <plugin>`) do, when a staged path matches their glob.
- CI's Claude Code: `validate` and `win32` run the hooks modules' kits on the engine `vellum/types/claude-code.d.ts` was written by. The step before `jdx/mise-action` and the action's `cache_key` are written once, in `validate`, as the YAML anchors `pin-claude-code` and `claude-cache-key` that `win32` aliases, so the two jobs cannot pin or cache that engine apart; each job keeps its own tool list (`install_args`). The step reads the version on that file's first line, prints it, and exports it as `MISE_CLAUDE_VERSION`, so mise installs that exact build in place of `claude = "latest"`. An exact version escapes mise's minimum release age, which keeps a fresh release out of `latest`, and the action's cache, whose key ends with that version (`cache_key`) while `latest` stays where the cache first resolved it: each pinned build is downloaded once per cache scope, then restored. A change under `vellum/types/` reaches every suite and kit (`scripts/gates/affected.ts`): a types update is tested on its own engine, every module's kit included, as soon as its pull request opens. A kit red in CI and green locally: compare that printed version with `claude --version` first.
- No Claude Code hook of this repository refuses a push: the ruleset of `dev` refuses every direct push to it, the owner's machine carries a global `guard-git-push` hook that refuses a push to `main` of a public repository, and the GitHub rulesets accept a fast-forward push to `main` ([GitHub branch protections](protections.md)).
- The factory's verify hooks, in a cloud session alone: `.claude/hooks/require-verify.sh start`, on SessionStart, records the working tree the session starts from, once per clone; `require-verify.sh record`, on PostToolUse of the `Skill` tool, records the working tree when the `verify` skill runs; `require-verify.sh stop`, on Stop, sends the session back to `verify` while the tree differs from both records, twice in a row at most. A session that changed nothing since it started is let through, on a branch that already holds commits too.
- The cloud session's tools: `.claude/hooks/cloud-tools.sh`, on SessionStart in a cloud session alone, runs `mise install --locked` in `.github/factory/` and links the shims into `~/.local/bin`, and tells the session when the environment ran another setup script than the clone's ([Cloud environment](cloud.md)). It never blocks.
- Claude Code PostToolUse, Stop and SubagentStop hooks: `.claude/hooks/format-on-edit.ts` applies oxlint's safe fixes to each edited file, formats it and never blocks; the agent-hooks kit runs `scripts/gates/run-gates.ts`, scoped as in `pre-push`, at the end of a main-session turn or a subagent's whose scope is not empty (`.claude/agent-hooks.jsonc`), and blocks while a gate is red and the agent makes progress. Contract and ceilings: `.claude/rules/hook-ladder.md`.

## CI

Triggers on `pull_request` to `main`/`dev` (opened, synchronize, reopened), on `push` to `dev` and `main`, and on `workflow_dispatch`. `main` is in the push list as a backstop: a ref update reaching it outside the release path still gets validated. The guard checks that `main` is an ancestor of `dev` (`git merge-base --is-ancestor`): `main` must always be a fast-forward prefix of `dev`.

The jobs follow the table of [Which suite runs on which trigger](#which-suite-runs-on-which-trigger). `test` is the check of this workflow that the ruleset of `dev` requires, and `main` requires it beside `validate` ([GitHub branch protections](protections.md)). It runs on a pull request and on a push: it needs `validate`, `scope`, `win32`, `mutation` and `e2e`, runs under `always()`, and fails unless `validate` and `scope` succeeded, `win32` and `mutation` succeeded or were skipped, and `e2e` succeeded whenever `scope` ran the browser suite. `validate` is the ladder above, and the one `scripts/gates/check-lint-config.ts` reads for parity: it runs on every event, with no job `if:`. On a push or a dispatch it is named `validate` and runs every suite and kit. On a pull request it is named `validate (scoped)` and its steps follow what the change reaches: the step `scope` runs `scripts/gates/affected.ts github-output` against the first parent of the merge commit the run checks out, the base's tip GitHub merged the head into (`baseOf`; the event's `pull_request.base.sha` can be older, and would count the commits landed since as the pull request's), the test step runs `affected.ts test --retry validate`, each of its suites retried once on a failure ([Flaky tests](#flaky-tests)), and each kit step keeps its `run:` word for word behind an `if:` on the `kits` output, so the parity check, which reads the `run:` lines alone, still finds every gate; `checkKitConditions` in `scripts/gates/check-lint-config.ts` holds each such `if:` to its own plugin's name. `scope` runs the same `affected.ts github-output` with `bun` alone installed, hands `all` and `units` to `win32`, and `e2e` to the browser suite's jobs (`reachesE2e`): true on every push and dispatch, since a push's `test` speaks for the whole tree, and on a pull request whose change against the base's tip touches a path of `isE2ePath` (`scripts/gates/e2e-paths.ts`). `win32` runs on `windows-latest`: `bun test --parallel vellum`, `claude plugin test vellum` and `bun test tools/platform`, the product's suites and the helpers every plugin copies, since Linux renames a folder another process holds and Windows refuses to, each retried once on a failure ([Flaky tests](#flaky-tests)). On a push or a dispatch it is named `win32` and runs; on a pull request it is named `win32 (scoped)` and runs when the scope is everything, as a change to `tools/` makes it, or holds `vellum`. `mise` installs `bun` and `claude` there and nothing else (`install_args`); the repository's own tooling under Windows (`scripts/`, `.claude/hooks`, lefthook, the shell linters) is not run. A job its `if:` skips reports success to a required check (GitHub's [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)), which is why `test` runs under `always()` and reads the results of the jobs it needs. `win32` may take a job `if:`: `test` reads a skipped one as a green one, and a pull request's run carries a name of its own, `win32 (scoped)`. `mutation` mutation-tests the lines a pull request, a push to `dev` or a dispatch changes ([Mutation testing](#mutation-testing)); a push to `main` skips it. `e2e-window` runs vellum's browser suite when `scope`'s `e2e` is true, one job per window: a matrix over the projects of `WINDOWS` in `vellum/e2e/playwright.config.ts`, with `fail-fast: false`, so a red window cancels none of the others. Each job, `e2e (<window>)`, runs `bun run --cwd vellum e2e -- --project=<window> --workers=4` after Playwright installs its Chromium with the runner's system libraries (`playwright install --with-deps`, which wants root: locally, `bun run --cwd vellum e2e:install` installs the browser alone). Under `CI` Playwright retries a failed test once ([Flaky tests](#flaky-tests)). It records no trace: `trace` in the config reads `CI`, which the runner sets, and no step uploads Playwright's `test-results/`, so a test red in CI is reproduced locally, on its file and project, where its trace is kept (`vellum/.claude/rules/tests.md`). `scripts/gates/e2e-windows.integration.test.ts` holds the matrix equal to the config's projects: a window added to one fails `bun test` until the other has it. `e2e-win32`, named `e2e (win32, light-1440)`, runs the same suite on `windows-latest` at `light-1440` alone, on the same condition; Playwright installs Chromium there with `e2e:install`, no system libraries. `e2e` is the browser suite's one verdict, which `test` reads: it needs the windows and `e2e-win32`, runs on the same condition, under `always()`, and fails unless every one of them succeeded, so a red or cancelled window turns it red. No hook runs the suite: it takes seconds per file, and `pre-push` already runs the gates. `flaky`, which never fails the run, opens, reopens or comments on one issue per test that passed on its retry, from the reports `validate`, `win32`, the windows and `e2e-win32` upload ([Flaky tests](#flaky-tests)). The workflow's token reads contents only; `flaky` alone gets `issues: write`.

A job its `if:` skips still leaves a check run on the SHA, concluded `skipped`: a pull request's head whose change reaches no path of the browser suite carries a `skipped` `e2e` and one `skipped` `e2e (${{ matrix.window }})`, the matrix never expanded; a push's to `main` a `skipped` `mutation`, and a pull request's that reaches neither `vellum/` nor everything a `skipped` check named by `win32`'s `name:` unrendered, `github.event_name == 'pull_request' && 'win32 (scoped)' || 'win32'`, and a fork's pull request a `skipped` `flaky`.

To run the browser suite on a ref whose change does not reach it:

- `gh workflow run ci.yml --ref <branch>`, on any ref: every job, `e2e` included. GitHub reads the `workflow_dispatch` trigger from the default branch's `ci.yml`. Whether its checks show in a pull request's checks list is not measured. They are check runs on the ref's head either way.

## Test tiers

`affected.ts test`, in `pre-push` and in `validate`, runs the suites it reaches in two tiers (`testRuns` in `scripts/gates/affected.ts`; the naming rule is `.claude/rules/test-tiers.md`):

| Tier | Files | Run |
|---|---|---|
| unit | every other `*.test.ts` and `*.spec.ts` | `bun test --parallel`, a worker per core, bun's 5 s per test; `--path-ignore-patterns` leaves the integration files out, `bunfig.toml`'s list repeated since the flag replaces it |
| integration | `*.integration.test.ts`, `*.integration.spec.ts`: a test file that starts a process or a server | the files by name, `--parallel` on half the cores (two at least, so 2 on CI's 4-vCPU runner), `--timeout=20000` |

Why: before the split, most red `validate` push runs on `dev` and `main` were a test cut at bun's 5 s, each one spawning `git`, `bun x tsgo` or a server, far slower in CI than locally while a test bound to a clock was not. A full run spawns tens of thousands of processes, most of them `git` (strace). Before the split, each such test got a `{ timeout }` of its own once it went red. A file joined the integration tier when strace counted one `execve` or more while it ran alone, or when it starts a server.

Cost, measured on four cores of a workstation (`taskset`): the unit tier runs in seconds; the integration tier takes over a minute and shortens with each worker added. CI's runner is not measured.

A path named on the command line still goes through `--path-ignore-patterns` (measured): the integration run names its files and passes no ignore list, so `bunfig.toml`'s applies. A scope's unit that holds integration files alone is left out of its unit run, since bun fails a run that finds no test file. Each flag is one argument, `--name=value`: the retry keeps the arguments that start with `-` and drops the rest ([Flaky tests](#flaky-tests)). `win32` runs vellum's suites in one run on the integration budget, since it calls no `affected.ts`. Plain `bun test --parallel` still runs both tiers, on bun's 5 s.

## Flaky tests

CI runs a failed test once more, goes green when that run passes, and keeps one issue labelled `flaky` per test that did so (`scripts/ci/flaky-report.ts`): a flake holds no landing, and each one is counted.

| Suite | The retry | A flake, and its id |
|---|---|---|
| `validate`'s suites, each `bun test` run of `affected.ts test --retry validate` | `retry bun`, as `win32`'s below, run by `affected.ts` on each of its runs in turn; the step stops at the first run still red after its retry | as `win32`'s below |
| `win32`'s `bun test --parallel --timeout=20000 vellum` | `retry bun`: the first run writes a junit report; on a failure, the files of its failed cases run again (`./<file>` each) with the options that start with `-`, so each option is one argument, and the step exits as that second run does; both reports are removed before the first run, so none an earlier run left is read | a case failed in the first report whose file the second report names, with no failure of that case, so an `afterAll` that threw once, `(unnamed)`, which a green rerun does not list, counts: `<file> > <classname> > <name>` |
| `win32`'s `claude plugin test vellum` | `retry kit`: on a failure, the whole kit runs again, since it takes no file filter; the step exits as the second run does | a `(fail)` line of the first run, `the file did not load` included, whose file the second run printed with no `(fail)` for it: `kit:<file> > <name>` |
| the browser suite, in each window and `e2e-win32` | Playwright's own, `retries` 1 under `CI` (`vellum/e2e/playwright.config.ts`), whose JSON reporter writes `vellum/test-results/playwright.json`; `playwright` reads it after the suite, red or green | a test Playwright marks `flaky`: `e2e:<file> > <describes> > <title>`, the window left out, so a test flaky in several windows has one issue |

Bun's retry is the script's, not `bun test --retry`: Bun reports a test that passed on its retry exactly like one that passed at once, with no mark in its console output, its junit report or its exit code. A retry of the files junit names cannot see a failure junit leaves out: a file that throws while loading is missing from the report while the console counts it. So `retry bun` retries only when the console's count of failed tests equals the report's and it counts no error; otherwise the step fails as the first run did, and says why. The kit is retried only when its output names a failed test.

Each writes `flaky-reports/<runner>.json` (`bun`, `kit`, `e2e`), a retry given `--report <name>` `flaky-reports/<name>.json` (`win32`'s `bun-platform`, beside its `bun`), and `validate` one per `bun test` run, `validate-<n>.json`: `{job, runUrl, flakes: [{id, runner, firstFailure}]}`, the run's URL ending with its attempt. Each job uploads `flaky-reports/*.json` under `if: ${{ !cancelled() }}`, red or green, as the artifact `flaky-<job>-<attempt>`: `flaky-validate-1`, `flaky-win32-1`, `flaky-e2e-light-1440-1`, `flaky-e2e-win32-1`. A name per attempt keeps the first attempt's report beside a re-run's.

`flaky` needs `validate`, `win32`, `e2e-window` and `e2e-win32`, and runs under `always()` after them, `validate` running on every event, on a push, a dispatch, or a pull request from this repository: a fork's token cannot write issues. It downloads every `flaky-*` artifact of the run, the earlier attempts' included, each to a folder of its own, and runs `report flaky-reports` with its own `issues: write`; no artifact is no flake. It is bookkeeping, never a verdict: every step carries `continue-on-error: true`, the checkout and the tool setup too since the job runs on every event, so a failure there, `gh`'s included, fails the step, visible in its log and as an annotation of the run, while the job, its check run and the workflow run still conclude `success` (GitHub's `steps.<id>.outcome` is the step's result before `continue-on-error`, its `conclusion` the one after; a green check over a failed step is reported in SignalK/signalk-server#2800). On the job instead, `continue-on-error` keeps the workflow run green but leaves the job's own check run at `failure` (reported in TensorAuto/OpenTau#293), which `gh pr checks` and the pull request's checks would show red. Neither behaviour is measured here.

| Fact | Owner |
|---|---|
| a test's issue | the newest open issue labelled `flaky` whose body holds `<!-- flaky:<id> -->`, else the newest closed one |
| a job's run recorded | a text, body or comment, of any issue holding the test's marker, holding `<!-- flaky-run:<run URL> <job> -->` |

- A flaky test with no issue: the label is created or reset (`gh label create flaky --force`), and the issue opens, titled `Flaky: <id>`, its Problem and Evidence naming the run, the job and the first failure; each other job of the run that saw it adds a comment.
- A flaky test with an open issue: a comment per job of the run that saw it, never an edit of a counter, so the issue's comments count its flakes.
- A flaky test whose issue is closed: the issue is reopened (`gh issue reopen`), then each job of the run that saw it adds its comment.
- A job's run recorded already, as when a re-run downloads the first attempt's report again: nothing, and a closed issue stays closed.

An issue labelled `flaky` with no marker, such as one naming a hang across several tests, is never matched: a flake of one of those tests opens its own issue.

The job has no `concurrency` group: GitHub cancels a pending job of a group that a third one replaces, whatever `cancel-in-progress` says ([Control the concurrency of workflows and jobs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)), and a `cancelled` `flaky` shows red on its pull request. Two `flaky` jobs that run at once can both find no issue for a test and open one each: at worst one duplicate, after which every comment goes to the newest open issue and a run either one records counts as recorded. Two that both find a test's issue closed both reopen it, the second reopen doing nothing, and both comments land: the reopen and the comment are two `gh` calls, since `gh issue reopen --comment` posts nothing on an issue open already (`reopenRun` in gh's `pkg/cmd/issue/reopen/reopen.go`), which would lose the second job's record. The job lists the `flaky` issues, open and closed, without their comments, since `gh issue list` reads only the first 100 of each (`issueComments` in gh's `api/query_builder.go`), then reads every comment of each issue a flake of the run marks, page by page (`gh api --paginate`). Windows' path separators in junit's `file` and Playwright's are not measured: both are turned forward. `scripts/ci/flaky-report.integration.test.ts` holds the three readers on the spike's outputs, `decide` on a new flake, a known one, none, one test from two windows or jobs, a closed issue reopened or left closed, and two open issues a race left, `retry bun` on a real `bun test` whose test, or whose `afterAll`, fails once, and the wiring in `ci.yml`.

## Mutation testing

`mutation` runs StrykerJS, under its command runner on `bun test`, on the modules `stryker.config.ts` lists in `mutate` that a change reaches, through their own lines or through the `.test.ts` beside them. `scripts/ci/mutation.ts` reads the hunks off `git diff -U0` from the merge-base with the base `affected.ts` resolves (`--base <ref>`, else a pull request's merge commit's first parent, else a push's `before`, else `origin/dev`), then runs one Stryker pass per module reached: the module whole, each mutant against its `.test.ts` alone, so a flaky suite of another module never kills its mutants. Whole, since Stryker keeps a mutant of a line range only when its whole node lies inside it: a block or a condition that spans past a changed line would go untested. A hunk that only deletes changes the two lines around its cut. String-literal mutants are left out (`excludedMutations`): the unit tests pin behaviour, not the wording of a message. Two kinds of undetected mutant fail the job:

- one whose lines meet a changed line of the module;
- when the module's `.test.ts` changed, one the base's tests killed: a second pass runs the module and its tests as the merge-base had them (`git archive` into a directory of its own), and each head mutant is matched to its base twin by mutator, replacement, and the line it sat on there, so a weakened test fails even where the module did not change.

Each failure is one line, file, line and column, status, mutator, then the code and its replacement, and `(killed at the base)` for the second kind; the module's summary counts the undetected ones elsewhere, the gaps the change did not make. A changed line, then a deleted test:

```
agent-hooks/config.ts:<line>:<column> Survived EqualityOperator: 0 >= value => 0 > value
mutation: agent-hooks/config.ts: 484 mutant(s) tested, 4 undetected on the changed lines, 74 elsewhere, outside this change
```

```
agent-hooks/config.ts:<line>:<column> Survived ConditionalExpression: typeof value === "number" => true (killed at the base)
mutation: agent-hooks/config.ts: 484 mutant(s) tested, 0 undetected on the changed lines, 5 killed at the base and undetected now, 78 elsewhere, outside this change
```

Its first step, `mutation.ts github-output`, needs `bun` alone: with nothing changed in a listed module or its `.test.ts` it writes `mutate=false`, and the job ends green with nothing installed. It runs when a pull request opens, reopens or gets a push. It runs on a push to `dev`, against the push's `before`, where a survivor turns the push run red, which `trunk-red.yml` hands to the factory; a pushed commit that already has a green `mutation` check, from the pull request that tested it, skips the passes (`testedAlready`, with `checks: read`). And it runs on a dispatch. A push to `main` skips it: the release moves `main` to a `dev` head tested already. Locally, `bun ./scripts/ci/mutation.ts run` runs the same check against `origin/dev`.

- In a sandbox: Stryker copies the repository under `.stryker-tmp/` (gitignored), the other checkouts under `.claude/worktrees/` left out (`ignorePatterns`), and mutates the copy, so the working tree never holds a mutant, not even when a run is killed: `mutation.integration.test.ts` kills a pass while its mutants run and compares every file's bytes and mode with what they were. It is no `EXPECTED_COMMANDS` entry and runs in no hook: each module is a Stryker run of its own (below), and `run-gates.ts` runs at every Stop.
- A module joins `mutate` once a run of it kills by assertion alone: a git fixture under Stryker's parallel runs can kill a mutant by timing out. `agent-hooks/config.ts`'s tests read temporary files and start no process: its kills are all assertions. `scripts/releasing/changelog.ts` joins once its pure tests are split from its fixtures. `mutation.integration.test.ts` fails while a listed module has no `.test.ts` or `.integration.test.ts`.
- The cost of a whole module is not measured on the CI job. The community Bun runner's per-test coverage gave no gain at a diff's lines, and was not measured on a whole module.

## Which suite runs on which trigger

A pull request's `validate` and `win32` run what its change reaches, and a push or a dispatch everything. `e2e` runs on every push and dispatch, and on a pull request whose change touches a path the browser suite covers. `test` reads them all, and the rulesets require it; `main` requires `validate` beside it, a name a pull request's run never reports.

| Trigger | `validate`, `win32` | `e2e` | `mutation` |
|---|---|---|---|
| PR push, any commit | scoped: `validate (scoped)`, and `win32 (scoped)` when the change reaches `vellum/` | when the pull request touches an e2e path, a job per window and one on Windows | the change since the merge commit's first parent |
| Push to `dev` | everything, never cancelled | yes | the change since the push's `before`, unless its commit has a green `mutation` check |
| Push to `main` | everything | yes | no |
| `workflow_dispatch`, any ref | everything | yes | the lines changed since `origin/dev` |

The table holds ([CI](#ci)). Two measurements set the shape of the `e2e` jobs:

- One job per window (`--project=<window>`), behind one aggregate check named `e2e`. Four workers per window ran a full run somewhat faster than two, so each window runs on 4; a window's suite step gains less than its spread between runs at 4, and the spread at 2 is not measured.
- CI runs the suite with tracing off, and a local run still keeps a failing test's trace ([CI](#ci)). Measured locally, tracing off cuts the median test's time by about a fifth. In CI, the one run without tracing was faster, but its window medians overlap the traced runs', so the size of the cut in CI waits for more runs.

The e2e paths have one owner, `scripts/gates/e2e-paths.ts`. They cover `vellum/**`, `docs/plugin-testing.md` (cited by the fixtures, asserted by `labels.e2e.ts`), `mise.toml` and `.github/workflows/ci.yml`. They leave out what the suite never loads: `vellum/src/runtime/hooks/**`, `vellum/src/steps/*/hooks.ts`, `vellum/hooks/`, `vellum/skills/`, `vellum/agents/`, the engine's types in `vellum/types/` (type-only, erased before the page or the server runs), the manifest `vellum/.claude-plugin/plugin.json` (the suite reads its version at run time, `vellum/e2e/settings.e2e.ts`, so a bump changes no result), `vellum/scripts/`, `vellum/src/review/hooks.ts`, the plugin's own instructions (`vellum/.claude/`, the Markdown at `vellum/`'s root), `*.spec.ts` and `*.test.ts`. A new directory under `vellum/` is inside by default.

Why:

- The cost. Run as one job on two workers, a full `e2e` took over ten minutes, nearly all of it the suite, against about a minute for `validate`; one job per window on four workers brings a full run down to a few minutes. A pull request that reaches no e2e path pays none of it.
- A pull request is squashed onto a `dev` that may have moved since its checks ran, so the push to `dev` runs the suite again on the commit that landed, and `trunk-red.yml` hands a red one to the factory.
- The time goes per test, not per window: a short test takes as long as the median one, since each test starts its own `preview.ts` (`vellum/e2e/harness.ts`), and each window pays its setup once. One job per window shortens a full run (above).
- No `concurrency` group: a run never cancels another, and `validate` must finish on every `dev` head, since [Git procedures](git.md) Release releases only a green one.

Rejected:

- `--only-changed`: Playwright follows the test files' imports, and those never reach the spawned server or the page bundle.
- Caching the browser: Playwright's CI guide advises against it, and the install is short.
- A merge queue: GitHub offers none in a personal account's repository.
- A filter per zone: `runtime/page`, `runtime/server` and the markdown rendering are loaded by every test file.
- Fewer windows: the matrix takes away the wall-time reason to drop any.
