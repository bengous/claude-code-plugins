# Git procedures

[Repo operations index](../repo-ops.md). Read before a push, landing or release. The branch model and lane choice live in `AGENTS.md`.

## Fast-forward flow

`main` is a delayed pointer on `dev`'s history, never a divergent branch. `origin/dev` is the source of truth; local `dev` checkouts are caches:

- Land a branch (remote-first, once, when validated): `bun ./scripts/land.ts <branch>`, from any checkout or worktree. It runs `origin/dev`'s copy of itself, extracted with `git archive origin/dev scripts agent-hooks` to a temporary directory, so a branch that edits the landing lands under the rule already on `dev`. It refuses before any push unless the branch is `feature/`, `fix/`, `renovate/` (Renovate's pull requests) or `chore/claude-code-types` (the types pipeline's, [Hooks](../plugin-testing/hooks.md)), the checkout holding it is clean, and its pull request is open against `dev` with every check green on the head that checkout holds. Then it runs `git fetch origin`, `git rebase origin/dev`, refuses a rebased branch that changes a path of `profile.review.risky` without a clean review verdict for its patch (next item), back at its reviewed head, then `bun install --frozen-lockfile` when the rebase changed `package.json` or `bun.lock` (the pre-push gates read that checkout's `node_modules`), `git push --force-with-lease origin <branch>` and `git push origin <branch>:dev` in that checkout, and starts over from the fetch, three times at most, when the `dev` push is rejected because `origin/dev` moved. When the branch touches the e2e paths, `e2e` runs on request only: between the two pushes, add the `e2e` label to its pull request (`gh pr edit <branch> --add-label e2e`), wait until the label is gone, which the run it started takes off as it begins (`until [ "$(gh pr view <branch> --json labels --jq 'any(.labels[]; .name == "e2e") | not')" = true ]; do sleep 5; done`), then watch that run, by then the branch's newest (`gh run watch "$(gh run list --branch <branch> --event pull_request --limit 1 --json databaseId --jq '.[0].databaseId')" --exit-status`). Not `gh pr checks`: it shows, per name, the check that started last on the head (`eliminateDuplicates` in gh's `pkg/cmd/pr/checks/aggregate.go`), and `e2e` is created only once the five windows are done ([CI](checks.md#ci)). Until then it shows the head's previous `e2e`, the push run's skipped one or an earlier run's verdict, and a loop reading it can end on the wrong run. The pre-push hook refuses the push to `dev` while that SHA has no green `e2e` run ([Local checks](checks.md)). An `e2e` that ends red or cancelled is re-run with `gh run rerun <run-id> --failed`, the command the refusal names: it re-runs the red windows and the `e2e` after them, waited for with `gh run watch <run-id>`, and pushing the same SHA again starts no run. A rejected push to `dev` means `origin/dev` moved in between: repeat from the fetch, which makes a new SHA that needs the label again; the loop converges because the branch is finished. GitHub marks the PR merged because the reviewed head SHA reaches the base; a rebase after the last reviewed push of the branch breaks that detection — then `gh pr close` with the integration SHA. The GitHub merge button is never used for a single branch; rebasing locally keeps commits signed by the author's key (GitHub-side rebase would strip signatures and trip `Require signed commits`).
- Review verdict: an agent that reviews a pull request (`/code-review <number>`) and leaves no finding open runs `bun ./scripts/review-verdict.ts record <branch> --sha <reviewed head>`, refused unless that head is still the pull request's, so a push after the review gets no verdict. It posts a comment whose first line is `<!-- review: clean patch-id=<id> -->`, the `git patch-id --verbatim` of the diff from the pull request head's merge-base with `origin/dev` to that head: whitespace counts, since indentation carries meaning in YAML. `land.ts` lands a branch that changes a path of `profile.review.risky` only when such a comment, by an account that can push (`authorAssociation` `OWNER`, `MEMBER` or `COLLABORATOR`), names the patch-id of the branch rebased on `origin/dev`. It reads the globs from `origin/dev`'s `.claude/agent-hooks.jsonc`, never the branch's, so a branch cannot loosen the rule it lands under. While that file does not read, every changed path counts as risky: a verdict still lands the branch that repairs it. A rebase that leaves the diff as it was keeps the verdict. A commit after the review needs a new review and a new record; so does a rebase that changes the lines around a hunk, after the branch is rebased and pushed, as the refusal says. A branch that changes no risky path needs no verdict.
- Land a stack (`gh stack`, one pull request per layer, each based on the branch below): `gh stack merge <stack-number> --squash --yes`, once every layer is reviewed. Not the push above: it lands the code, but GitHub marks a pull request merged only when its head reaches its own base, so every layer above the bottom one ends closed, not merged (the grill stack, #197 to #209). Squash is the one method the rules let through: a merge commit breaks `Linear history on dev`; rebase merge is off in the repository, and GitHub recreates rebased commits unsigned, which `Require signed commits` refuses; GitHub signs a squash, and under required signatures only the pull request's author may squash. Each layer lands as one commit suffixed `(#N)`, with no version bump: the release makes those. The merge runs on the server, so the pre-push `e2e` gate never sees it; hold it by hand first. A stacked pull request gets no `pull_request` run (`ci.yml` triggers on `main` and `dev` bases only): `gh workflow run ci.yml --ref <layer-branch>` on each layer's final head, watched green. Then `git merge-base --is-ancestor origin/dev origin/<top-branch>`: when it holds, the tree that lands is the tree the top layer's run tested; otherwise `gh stack rebase`, `gh stack push`, and dispatch again. `delete_branch_on_merge` is off: sweep the layer branches after, their local copies with the `git-sweep:auto-sweep` skill (below), their remote ones with the user through `/git-sweep`.
- Plugin sessions after a landing: once the catalog units are activated, `claude-plugin-catalog.path` watches the `origin/dev` reflog and runs `scripts/plugin-catalog.ts sync` from the locked catalog worktree. No pull or plugin update is needed for sessions. This does not refresh a local `dev` checkout. Setup, recovery and the pending live verification are in [Managed catalog](../plugin-testing/catalog.md).
- Refresh a stale local `dev` after a landing: `git pull --ff-only` from the checkout holding `dev`. Never land through a local `dev` that might be stale — that is how a fast-forward publish turns into a rejected push and a hand-recovered rebase.
- Clean up after a landing or at the end of a session: the `git-sweep:auto-sweep` skill, from any checkout. It judges against `dev`, deletes with no prompt the local branches it proves already there, removes the clean agent worktrees (`.claude/worktrees/agent-*`) standing on them, and archives an abandoned agent branch under `refs/archive/<branch>` before deleting it; `git branch <branch> refs/archive/<branch>` restores one. It deletes no remote branch, and keeps a locked or dirty worktree, one holding an ignored path a checkout does not regenerate (a `plans/`), and every named worktree, each with its branch. What it keeps and why, and the thresholds: [git-sweep's README](../../git-sweep/README.md). Agents never type `git branch -D`, `git worktree remove` or `git push --delete` for this.
- Inline work on `dev`: `git pull --ff-only` first, commit, `git push origin dev` when validated; on rejection `git pull --rebase`, push again. A commit that touches the e2e paths takes a branch instead: the pre-push hook refuses it on `dev` without a green `e2e` run on its SHA.
- Issue footers: `Closes #N` fires on `main` (the default branch), not on `dev`. Issues referencing landed commits stay open until the release push, or are closed by hand with the SHA.
- Release, the human's step, once the human has emptied, or accepted item by item, what the landed PRs list as not measured: `bun ./scripts/release.ts --dry-run`, read its plan, then `bun ./scripts/release.ts --plan <digest>` with the digest it printed.
  - The dry-run lists each marketplace plugin changed since `main` with its `plugin.json` version unchanged, a change to its documentation alone aside (`scripts/check-plugin-bumps.ts`). For each, the commit subjects propose a level (`!` major, `feat` minor, else patch, one step lower under 0.x), and a headless `claude -p --model opus`, with no tool, setting file, hook or MCP server, judges the level, the commit summary and, for a plugin that keeps a `CHANGELOG.md`, the section, all checked by code (`scripts/release-plan.ts`). Claude's level applies; the subjects' is shown beside it when they differ. A failed call or an answer that does not check fails the dry-run. It prints each bump, the tags the release makes and the digest of the plan, sealed in `$(git rev-parse --git-path release-plan)/<target>.json`; a dry-run run since, by an agent, writes a plan of another digest and changes nothing the human read. `--dry-run <sha>` plans an older SHA, refused when a plugin needs a bump there: a bump lands on `dev`'s head. CI runs on push heads only, so the releasable commits are the SHAs that were once a pushed `dev` head.
  - `--plan <digest>` applies that plan's bumps, and makes no tag the plan did not print. In a temporary worktree on the plan's target, with the root dependencies installed for the hooks, it makes one `chore(<plugin>): x.y.z, <summary>` commit per bump, the changelog section with it, and pre-commit's `sync-versions` writes the version into the catalog entry and the README row. It pushes them to `dev`. When `dev`'s head, fetched before each push, is not their base, it rebases them on that head first, three attempts at most; a refused push is tried again when `dev` moved meanwhile, whatever git answers, its pre-push hook's minutes included, and otherwise refused with git's output, the same `--plan <digest>` good again once what it names is fixed. It refuses, nothing pushed, and asks for a new dry-run when `main` moved, `dev` no longer holds the plan's target, the new commits touch a plugin the plan bumps or make another need a bump, the rebase conflicts, or the rebased head would make a tag the plan did not print. The commits `dev` gained ship with the bumps: before `main` moves, it prints the head `main` reaches and each commit past the plan's target, one line each. The worktree is removed whatever happens.
  - It then waits for that commit's `push` run of `ci.yml` to end green, the whole run (`scripts/ci-wait.ts`), runs `git push origin <commit>:main`, and for each plugin that keeps a `CHANGELOG.md` and changed version creates the annotated tag `<name>-v<version>` on the commit that set that version, pushes it, and publishes its GitHub Release from the tag's message: the changelog sections newer than the version `main` held. Everything is checked before a push, so a changelog that does not parse or a tag that already exists leaves `main` unmoved. Once the bumps are on `dev`, a red run, a wait that fails or a refused push to `main` stops it with `main` unmoved, and its message names the bump commit on `dev`: re-run the red jobs (`gh run rerun <run-id> --failed`) or fix what it names, then a new `--dry-run` and `--plan`, whose plan finds the bumps made and only waits for CI and pushes `main`. A step that fails after the push to `main` is named, and is finished by hand.
  - The pre-push hook refuses a push to `main` that leaves a changed plugin unbumped, and names each one ([Local checks](checks.md)); `bun ./scripts/check-plugin-bumps.ts origin/main origin/dev` lists them after a `git fetch origin`. The rulesets guarantee a fast-forward is the only kind of push `main` accepts.
- Force pushes happen only on feature branches (`--force-with-lease` after a rebase), never on `dev` or `main`.

## Sampled review

The human reads a sample of what landed on `dev` each week, not every commit. `bun ./scripts/sample-review.ts` picks the sample and reviews nothing: the review is the reader's, or a `/code-review` run it prints. It reads `origin/dev` as it is, so `git fetch origin` first.

- The pool: the non-merge commits whose committer date falls in an ISO week, Monday 00:00 to the next, UTC: the last complete one, or the one `--week <YYYY-Www>` names. Run on any day of a week, it samples the same week, and a commit belongs to the draw of exactly one week. A version bump (`chore(<scope>): x.y.z`) and a commit with no code in it are left out: documentation (Markdown, except under a `skills/`, `agents/`, `commands/` or `.claude/` directory and a `*.prompt.md`, which agents load as instructions) and lockfiles are not code.
- The draw: `--count` commits, 3 by default, each weighted by the square root of its code lines and seeded by the ISO week. It is weighted sampling without replacement with nothing random in it: the same week and the same commits give the same sample, whatever their order, and a commit entering or leaving the pool changes it only if that commit is, or outdraws, a pick.
- The report, oldest first: SHA, subject, files, lines, and the review of that one commit, `/code-review <sha>^..<sha>` ([Choose what to review](https://code.claude.com/docs/en/code-review-local#choose-what-to-review)). When the commit's pull request body carries the `<!-- opened_by: <session id> -->` line `github-flow:pr` writes, found with `gh pr list --state all --search <sha>`, the report adds `claude --resume <session id>`, then `/hindsight debrief` in it. No such line, no hint; a `gh` that fails is named once under the list.
- An empty week, or one whose commits are all left out, prints `no commit to sample` and exits 0.

## Friction report

`bun ./scripts/friction-report.ts` counts the frictions of the agent workflow over an ISO week, the last complete one or the one `--week <YYYY-Www>` names, and prints each beside the friction audit's average per 7 days, so a change meant to remove a friction is judged by a number. It runs on the workstation only, where the transcripts and the denial log live. It reads `origin/dev` as it is (`--ref`), so `git fetch origin` first.

- Sources: the Claude Code transcripts of every directory under `~/.claude/projects` whose name holds `claude-code-plugins`, subagents included (`--projects-dir`); the auto-mode denial log `~/.local/state/claude/permission-denied.jsonl`, written by the dotfiles' `PermissionDenied` hook (`--denial-log`); the commits of `origin/dev` by committer date, as the sampled review reads them (`landedIn`); `gh issue list --label flaky`. A transcript event counts in the week its own timestamp falls in, whatever file holds it, and once, by its uuid, when a resumed session copied it into a second file. An old week reads as long as Claude Code keeps its transcripts (`cleanupPeriodDays`).
- The counters:

  | Counter | What counts |
  |---|---|
  | release refusals | A main-session user message, the output of a `!` command or pasted terminal output, holding both the release guard's `Bump each version in its plugin.json` and git's `failed to push some refs to '…bengous/claude-code-plugins…'`; one per session. A message an agent sent the session (`<task-notification>`, `<teammate-message`, `<agent-message`, `Another Claude session sent a message:`) does not count, whatever it quotes. A refusal never shown to a session is not seen. |
  | agent CI waits | A Bash call matching `CI_WAIT`: `gh run watch`, `gh pr checks --watch`, or a loop or a `sleep` around `gh run`, `gh pr` or `gh api`. Its foreground time runs from the call to its result; a background call adds none. |
  | agent git pushes | A Bash call that runs `git push`, timed the same way. The time is the whole call's: the push with its pre-push hooks and network, and whatever else the call chains, a commit and its hooks, tests, a CI wait, a push of another repository. It bounds what the pre-push hooks cost from above. |
  | `!` commands typed | A user message opening with `<bash-input>`. Releases: `release-plugins` or `scripts/release.ts`. Destructive git: `branch -D`, `push … --delete`, `--force`, `push origin <ref>:dev`, `gh stack merge`. |
  | worktree isolation refusals | A tool result flagged as an error whose text says the session or the agent is isolated in the worktree, the command is too complex to verify, or the isolation context was lost. |
  | classifier denials | A denial log line whose `cwd` holds `claude-code-plugins`, listed by `reason` under the table. |
  | flaky issues | An issue labelled `flaky` opened in the week, and each comment posted on one in it. No such label, no issue. |
  | review follow-up commits | A subject holding `review of #`, `review's findings`, `second review` or `answers the review`. |
  | version bump commits | A subject the sampled review leaves out as a bump, `chore(<scope>): x.y.z` (`VERSION_BUMP`). |

- The baseline, `BASELINE`: the audit's totals from 2026-09-21 to 2026-10-19, both days included, 29 days, counted by hand and divided per 7 days. A counter the audit did not count shows `-`. The script's counters, run over that window on 2026-10-20, found 479 CI waits (8.92 foreground hours), 318 isolation refusals, 15 destructive and 11 release `!` commands, 73 review follow-ups, 64 bumps and 4 release refusals, against the audit's 490 (9.18 h), 329, 17, 11, 74, 64 and 4. Ten of the 11 CI waits apart are events copied into a second transcript, which the script counts once.
- A counter it cannot read prints `?`, with the reason under the table: a missing denial log, a `gh` that fails. Transcript or log lines that do not parse are left out, and their number goes there too.

## Why fast-forward

Merge commits on `main` accumulated as an ever-growing ladder `dev` never received, and GitHub's rebase-merge re-creates commits unsigned, which once severed the `main`/`dev` common ancestor. Local rebase plus fast-forward push keeps one linear signed history where `main` is a prefix of `dev` by construction.
