# Git procedures

[Repo operations index](../repo-ops.md). Read before a push, landing or release. The branch model and lane choice live in `AGENTS.md`.

## Fast-forward flow

`main` is a delayed pointer on `dev`'s history, never a divergent branch. `origin/dev` is the source of truth; local `dev` checkouts are caches:

- Land a branch (remote-first, once, when validated): `bun ./scripts/land.ts <branch>`, run once in the background, from any checkout or worktree. It waits by itself, an hour at most, and ends on one verdict line: `landed …`, or `land: <why>`, which names what to do next. No CI wait, `e2e` label or `gh run watch` is written by hand around it. It runs `origin/dev`'s copy of itself on the arguments as given, extracted with `git archive origin/dev scripts agent-hooks` to a temporary directory, so a branch that edits the landing lands under the rule already on `dev`. It refuses before any push unless the branch is `feature/`, `fix/`, `renovate/` (Renovate's pull requests) or `chore/claude-code-types` (the types pipeline's, [Hooks](../plugin-testing/hooks.md)), the checkout holding it is clean, and its pull request is open against `dev` with the head that checkout holds, which a push shows within a minute. Then it waits until every `ci.yml` `pull_request` run of that head is green (`scripts/ci-wait.ts`). It reads each run's `status` and `conclusion`, never `gh pr checks`, which shows per name the check that started last on the head (`eliminateDuplicates` in gh's `pkg/cmd/pr/checks/aggregate.go`) and showed skipped jobs `in_progress` for minutes after their run had concluded on #361. A run red in its e2e jobs alone is re-run once, with `gh run rerun <run-id> --failed`, which re-runs the red windows and the `e2e` after them; any other red, or a red left after that re-run, ends the landing with the run's URL. When the branch touches the e2e paths and the head holds `origin/dev` but has no green `e2e` check run, the pre-push gate's own predicate (`refusalFor` in `scripts/check-e2e-green.ts`), it adds the `e2e` label to the pull request, taken off first when it is on, since adding a label already there starts no run, and waits for the run the label starts, told from the runs listed before it. A head that does not hold `origin/dev` gets no label: `dev` would take only its rebased commit, so it is rebased first. Then, in that checkout, it runs `git fetch origin`, `git rebase origin/dev`, refuses a rebased branch that changes a path of `profile.review.risky` without a clean review verdict for its patch (next item), back at its reviewed head, then `bun install --frozen-lockfile` when the rebase changed `package.json` or `bun.lock` (the pre-push gates read that checkout's `node_modules`), `git push --force-with-lease origin <branch>` and `git push origin <branch>:dev`. Before the rebase and before each push it checks that the checkout is still clean at the head it left there: a commit or an edit made while it waited ends the landing, left as it is, since it would land unreviewed. A rebase that makes a new commit on a branch touching the e2e paths waits again, for that commit's runs and its own `e2e` run: the pre-push hook refuses the push to `dev` while that SHA has no green `e2e` run ([Local checks](checks.md)). A `dev` push rejected because `origin/dev` moved starts over from the fetch; three attempts at most. GitHub marks the PR merged because the reviewed head SHA reaches the base; a rebase after the last reviewed push of the branch breaks that detection — then `gh pr close` with the integration SHA. The GitHub merge button is never used for a single branch; rebasing locally keeps commits signed by the author's key (GitHub-side rebase would strip signatures and trip `Require signed commits`).
- Review verdict: an agent that reviews a pull request (`/code-review <number>`) and leaves no finding open runs `bun ./scripts/review-verdict.ts record <branch> --sha <reviewed head>`, refused unless that head is still the pull request's, so a push after the review gets no verdict. It posts a comment whose first line is `<!-- review: clean patch-id=<id> -->`, the `git patch-id --verbatim` of the diff from the pull request head's merge-base with `origin/dev` to that head: whitespace counts, since indentation carries meaning in YAML. `land.ts` lands a branch that changes a path of `profile.review.risky` only when such a comment, by an account that can push (`authorAssociation` `OWNER`, `MEMBER` or `COLLABORATOR`), names the patch-id of the branch rebased on `origin/dev`. It reads the globs from `origin/dev`'s `.claude/agent-hooks.jsonc`, never the branch's, so a branch cannot loosen the rule it lands under. While that file does not read, every changed path counts as risky: a verdict still lands the branch that repairs it. A rebase that leaves the diff as it was keeps the verdict. A commit after the review needs a new review and a new record; so does a rebase that changes the lines around a hunk, after the branch is rebased and pushed, as the refusal says. A branch that changes no risky path needs no verdict.
- Land a stack (`gh stack`, one pull request per layer, each based on the branch below): `gh stack merge <stack-number> --squash --yes`, once every layer is reviewed. Not the push above: it lands the code, but GitHub marks a pull request merged only when its head reaches its own base, so every layer above the bottom one ends closed, not merged (the grill stack, #197 to #209). Squash is the one method the rules let through: a merge commit breaks `Linear history on dev`; rebase merge is off in the repository, and GitHub recreates rebased commits unsigned, which `Require signed commits` refuses; GitHub signs a squash, and under required signatures only the pull request's author may squash. Each layer lands as one commit suffixed `(#N)`, its version bump folded in. The merge runs on the server, so the pre-push `e2e` gate never sees it; hold it by hand first. A stacked pull request gets no `pull_request` run (`ci.yml` triggers on `main` and `dev` bases only): `gh workflow run ci.yml --ref <layer-branch>` on each layer's final head, watched green. Then `git merge-base --is-ancestor origin/dev origin/<top-branch>`: when it holds, the tree that lands is the tree the top layer's run tested; otherwise `gh stack rebase`, `gh stack push`, and dispatch again. `delete_branch_on_merge` is off: sweep the layer branches after (`/git-sweep`).
- Plugin sessions after a landing: once the catalog units are activated, `claude-plugin-catalog.path` watches the `origin/dev` reflog and runs `scripts/plugin-catalog.ts sync` from the locked catalog worktree. No pull or plugin update is needed for sessions. This does not refresh a local `dev` checkout. Setup, recovery and the pending live verification are in [Managed catalog](../plugin-testing/catalog.md).
- Refresh a stale local `dev` after a landing: `git pull --ff-only` from the checkout holding `dev`. Never land through a local `dev` that might be stale — that is how a fast-forward publish turns into a rejected push and a hand-recovered rebase.
- Inline work on `dev`: `git pull --ff-only` first, commit, `git push origin dev` when validated; on rejection `git pull --rebase`, push again. A commit that touches the e2e paths takes a branch instead: the pre-push hook refuses it on `dev` without a green `e2e` run on its SHA.
- Issue footers: `Closes #N` fires on `main` (the default branch), not on `dev`. Issues referencing landed commits stay open until the release push, or are closed by hand with the SHA.
- Release: `bun ./scripts/release.ts` (or `bun ./scripts/release.ts <sha>`; `--dry-run` first prints what it would push and tag), which runs `git push origin dev:main` and then, for each plugin that keeps a `CHANGELOG.md` and changed version, creates the annotated tag `<name>-v<version>` on the commit that set that version, pushes it, and publishes its GitHub Release from the tag's message: the changelog sections newer than the version `main` held. It reads and checks everything before the push, so a changelog that does not parse or a tag that already exists leaves `main` unmoved. A step that fails after the push is named, and is finished by hand. Run it once the head's `validate` run is green and the human has emptied, or accepted item by item, what the landed PRs list as not measured. The pre-push hook refuses it while a marketplace plugin changed since the remote's `main` and kept its `plugin.json` version, and names each one (`scripts/check-plugin-bumps.ts`, [Local checks](checks.md)): bump each in a `chore(<plugin>): X.Y.Z` commit on `dev` first, with its changelog section when the plugin keeps one. After `git fetch origin`, `bun ./scripts/check-plugin-bumps.ts origin/main origin/dev` lists them ahead of the push. CI runs on push heads only, so the releasable commits are exactly the SHAs that were once a pushed `dev` head; with a red head, either release the last green SHA (`bun ./scripts/release.ts <sha>`) or land a fix commit and release that. The rulesets guarantee this is the only kind of push `main` accepts.
- Force pushes happen only on feature branches (`--force-with-lease` after a rebase), never on `dev` or `main`.

## Sampled review

The human reads a sample of what landed on `dev` each week, not every commit. `bun ./scripts/sample-review.ts` picks the sample and reviews nothing: the review is the reader's, or a `/code-review` run it prints. It reads `origin/dev` as it is, so `git fetch origin` first.

- The pool: the non-merge commits whose committer date falls in an ISO week, Monday 00:00 to the next, UTC: the last complete one, or the one `--week <YYYY-Www>` names. Run on any day of a week, it samples the same week, and a commit belongs to the draw of exactly one week. A version bump (`chore(<scope>): x.y.z`) and a commit with no code in it are left out: documentation (Markdown, except under a `skills/`, `agents/`, `commands/` or `.claude/` directory and a `*.prompt.md`, which agents load as instructions) and lockfiles are not code.
- The draw: `--count` commits, 3 by default, each weighted by the square root of its code lines and seeded by the ISO week. It is weighted sampling without replacement with nothing random in it: the same week and the same commits give the same sample, whatever their order, and a commit entering or leaving the pool changes it only if that commit is, or outdraws, a pick.
- The report, oldest first: SHA, subject, files, lines, and the review of that one commit, `/code-review <sha>^..<sha>` ([Choose what to review](https://code.claude.com/docs/en/code-review-local#choose-what-to-review)). When the commit's pull request body carries the `<!-- opened_by: <session id> -->` line `github-flow:pr` writes, found with `gh pr list --state all --search <sha>`, the report adds `claude --resume <session id>`, then `/hindsight debrief` in it. No such line, no hint; a `gh` that fails is named once under the list.
- An empty week, or one whose commits are all left out, prints `no commit to sample` and exits 0.

## Why fast-forward

Merge commits on `main` accumulated as an ever-growing ladder `dev` never received, and GitHub's rebase-merge re-creates commits unsigned, which once severed the `main`/`dev` common ancestor. Local rebase plus fast-forward push keeps one linear signed history where `main` is a prefix of `dev` by construction.
